## Landed today

- **CONFIRMED** — `fcd3193` on `submain`: "feat(semantic): gene contract checking, Self resolution, method-ownership rules (0.3.4 slice 2 of 6, rebuild)." 594 insertions across 23 files. The major work:

  - **Pass 0 contract conformance**: The `collect_gene_phen_registry()` function now fully validates every phen against its gene. Checks arity (parameter count), parameter types (positional matching after Self-substitution), return type, missing methods, and extra methods. Each mismatch produces a targeted diagnostic naming the gene, method, position, and the expected-vs-got types.

  - **Self resolution**: `Self` in phen signatures and bodies is substituted to the concrete receiver type at the AST level *before* analysis, via a new `substitute_self_type()` function that recurses through `Array`, `Handle`, and `Result` wrappers. This is deliberate: substituting to a floating `TypeParam("Self")` would check nothing because `types_compatible` unifies any TypeParam with anything. A `map_stmt_types()` helper applies the substitution across all type-annotation positions in a statement tree.

  - **Method-ownership locked rule**: Three applications, all enforced. (1) No extra methods beyond the gene's contract — caught in Pass 0. (2) Impl method and phen method may not share a name on one type — caught during per-file impl-block analysis via the new `phen_methods` field on `Analyzer`. (3) One implementation per method name per concrete type across all genes — caught in Pass 0.

  - **PhenDef semantic representation upgraded**: `SemanticStmt::PhenDef` now carries `Vec<SemanticFunction>` and `Vec<Vec<SemanticParam>>` (receiver params) instead of just `Vec<String>` method names. Methods are analyzed in throwaway scopes exactly like impl-block methods.

  - **Self-outside-phen rejection**: A scan in `collect_gene_phen_registry()` detects `Self` used in function signatures or bodies outside of a phen definition. Prevents `Self` from silently resolving as an unknown struct name.

  - **10 new negative test fixtures + 1 positive**: `t_gene_phen_contract_arity`, `t_gene_phen_contract_missing`, `t_gene_phen_contract_param_type`, `t_gene_phen_contract_return_type`, `t_gene_phen_extra_method`, `t_gene_phen_impl_collision`, `t_gene_phen_self_leak_reject`, `t_gene_phen_two_gene_collision`, `t_self_outside_phen` (all expected-fail), and `t_gene_phen_contract_ok` (expected-pass, exercises two phens of one gene with Self in every type position as a leak canary).

## Decisions and direction

Both commits confirm and implement design decisions from `docs/post_0_1/gene_phen_design.md`:

1. **Self is concrete, not parametric** (design doc decision 3). The implementation substitutes Self to the receiver's real type before any analysis runs, exactly as the design specifies. The `t_gene_phen_self_leak_reject` fixture proves this isn't cosmetic — annotating an Enemy literal as `Self` inside a Player phen is a type error, not a silent pass.

2. **Dispatch reuses impl-block machinery**. Slice 3 registers phen methods into `semantic_impls` rather than adding a separate dispatch path. This confirms the design doc's position that phen methods are "full implementations exactly like an impl block's" — the runtime can't tell the difference.

3. **Method ownership is locked, not open** (design doc decision 5). All three ownership-rule applications are enforced: no extras beyond the contract, no name collisions between impl and phen methods, no cross-gene method name collisions on one type. The `t_gene_phen_impl_collision` and `t_gene_phen_two_gene_collision` fixtures exercise these paths.

4. **Slice 2 carries "rebuild" in its commit message**, suggesting an earlier version of this slice was discarded and rewritten. The final version is clean and well-tested.

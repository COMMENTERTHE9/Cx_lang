## Landed today

**Gene-bound soundness fix** (`e105e56`, 14:21) — CONFIRMED. A gene declares `fnc` signatures only, so a bound promises methods, not fields. But `resolve_field_access` had no arm for `TypeParam`, so `t.base` through a bounded parameter compiled and ran correctly for the author's intended type, then failed at runtime for any other conforming type — with the wrong diagnostic (§17's field-as-variable message). The fix adds a `TypeParam` arm to `resolve_field_access`, the C1–C4 choke point, so field read/write/compound-write are all covered by construction. `type_is_not_indexable` also gains the bare `TypeParam` for the same reason — `t:[0]` previously reached the interpreter and failed with the wrong message.

A prerequisite inconsistency was fixed on the way: three `DotAccess` sites resolved the receiver's type with an empty type-parameter scope, so `t: T` surfaced as an unregistered struct named `"T"` instead of `TypeParam("T")`. `MethodCall` already used the real scope; the three sites now match. Five new test fixtures pinning both the bounded and unbounded rejection messages, plus a canary that method dispatch through a bound still works.

Docs commit `6e57296` records the fix in `known_issues.md` §22 and adds the "check what the check sees" rule to `enforcement_layers.md`. Sequencing is explicitly noted: this was fixed *before* the monomorphizer so that pass is not built over an unsound access rule.

**Generic-function monomorphization** (`959a980`, 15:01) — CONFIRMED. New module `src/ir/monomorphize.rs` (~350 lines). One specialized `SemanticFunction` per (template, concrete-type-arguments) pair, emitted through the ordinary function-lowering path and called by a mangled name — the same shape phens already use. The key insight: `analyze_call` already derives the type substitution and was discarding it. `Call` now records it as `type_args`, and propagation is map composition, not re-derivation.

The walker covers all 23 `SemanticStmt` and 20 `SemanticExprKind` variants with no catch-all arm, so adding a variant is a compile error in the monomorphizer. Per-template cap of 64 instantiations against a corpus max of 2, with a diagnostic naming the template and first few types. The bounded case (gene-constrained type parameters) came along because the walker rewrites `MethodCall.struct_name`, which *is* the bounded case's job.

Four new test fixtures: specialization canary, struct return, transitive instantiation, and uncalled-template suppression. Docs commit `0ff36e5` records the fix in `known_issues.md` §23 (superseding the earlier §19 that filed generic functions as open).

**Interpreter call-depth guard** (`878ba7c`, 16:26) — CONFIRMED. `runtime.rs` gains a `call_depth: usize` field and a `MAX_CALL_DEPTH` of 256 (measured: deepest corpus recursion is 15, crash point is ~492 on a debug build). Both `call_semantic_func` and `call_semantic_method` carry the guard. New `RuntimeError::CallDepthExceeded` variant with function name and position, reported through the diagnostic path at exit 1 — not the 127 that used to collide with the SKIP sentinel. Cost measured on `fib(24)` (~150k calls): run-to-run variance dwarfs the guard's overhead.

This unblocked `t_mono_instantiation_cap`, the fixture that tests the monomorphizer's cap — the interpreter used to crash on it at exit 127, and the rejection-shape harness correctly refused to call a crash a diagnosis. Two new fixtures. Docs commit `50bd693` records §24 in `known_issues.md`.

**JIT call-depth guard** (`664850d`, 19:14) — CONFIRMED. Frame counter via `extern "C"` host callbacks (`cx_depth_enter` / `cx_depth_exit`), process-lifetime `AtomicUsize`, same shape as `cx_trap` and `cx_handle_new`. Reads the shared `MAX_CALL_DEPTH` constant so both backends agree on 256 frames exactly — a one-frame disagreement in the first version (counting `main`) was caught and fixed before commit.

A stack probe was explicitly disqualified: cheaper (2-3 instructions, no call), but terminates on bytes consumed, which varies per function and could never agree with the interpreter's frame-based limit. Cost measured on `fib(30)` (~2.7M calls): +29 ms, ~31%, ~11 ns per call — the upper bound, since programs without calls pay nothing.

This was the third and last instance of the crash-instead-of-rejection pattern: §15 (harness), §24 (interpreter), §25 (JIT). The evidence that the pattern is closed is `t_interp_recursion_guard`, a fixture that could not be written while either backend crashed. Docs commit `af29d1d` records §25 and declares the pattern closed.

## Decisions and direction

Three design decisions worth recording:

1. **Soundness before monomorphization.** The gene-bound fix was sequenced first explicitly, so the monomorphizer inherits a sound access rule rather than discovering it late. The docs commit records this as a placement guarantee.

2. **Frame-count guard, not stack probe.** Both backends now agree on a 256-frame limit. The alternative — a stack-byte probe — is cheaper but terminates on a value that varies per function, making cross-backend agreement structurally impossible. The cost was measured before the mechanism was committed (not after), and the measurement is filed in the docs.

3. **Exhaustive walker for monomorphization.** The new module matches every AST variant without a catch-all, turning a missed variant from a silent coverage hole into a compile error. This is the same design philosophy as the rejection-shape harness: "a fact the harness does not assert is a fact the project does not actually guarantee."

The `docs/frontend/enforcement_layers.md` update codifies the "check what the check sees" rule: analysis must look at the same resolved type the rest of the pipeline does, not a stripped version. The three `DotAccess` sites that were using an empty type-parameter scope are the concrete example.

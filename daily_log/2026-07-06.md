## Landed today

**CONFIRMED — `d4a7373` (submain, Jul 5 20:11): Guard clauses on `when` arms — second slice of 0.3.2 pattern matching**

Full-stack implementation of `if <expr>` guards on `when` arms. The guard expression is evaluated only after the pattern already matches, and any `as v` binding from the previous day's work is already in scope when the guard runs — the `t_pattern_guard_as_v_in_guard.cx` fixture proves this by using `v` inside the guard expression itself.

Parser changes: both the when-expression and when-statement parsers now accept an optional `just(Token::KeywordIf).ignore_then(expr.clone())` between pattern and `=>`. The `WhenArm` AST struct gained a `guard: Option<Expr>` field, placed on the arm (not on the pattern) because guards apply uniformly across every pattern kind.

IR lowering in `src/ir/lower.rs` (+293/-63 lines): the core change splits each arm's control flow into a guard evaluation block that branches to the body on true, or to the next arm's continuation block on false. This reuses the existing unknown-seam machinery — `guard_unknown_condition` rejects `unknown` guards the same way `if` conditions are rejected, and the continuation-block structure matches the existing when-arm fallthrough pattern.

Interpreter in `src/runtime/exec.rs` (+24 lines): the guard evaluates after pattern match and `as v` binding, reusing the exact truthiness rules from `if` conditions (Bool, TBool 0/1, Num != 0, and unknown/TBool(2) as hard error via `UnknownCondition`). A failed guard pops the arm scope and continues to the next arm.

Semantic analysis in `src/frontend/semantic.rs` (+24/-1): the guard expression is analyzed within the arm scope, so `as v` bindings are visible to it. `SemanticWhenArm` in `semantic_types.rs` gained a `guard: Option<SemanticExpr>` field.

10 new test fixtures:
- 4 positive: `true_enters`, `false_falls_through`, `as_v_in_guard` (composition), `discriminate_no_eval` (guard is not evaluated when pattern doesn't match)
- 6 negative (expected-fail): `runtime_unknown_reject`, `static_unknown_reject`, `scope_leak_outer`, `scope_leak_other_arm_guard`

**CONFIRMED — `c5e8e22` (submain, Jul 6 19:11): Float comparison bugfix in interpreter**

The interpreter's `ops.rs` had `Value::Float` match arms for `Eq` and `Ne` but was missing them for `Lt`, `Gt`, `LtEq`, and `GtEq`. Any f64 relational comparison (`3.14 > 2.0`) fell through to `BadOperands: operator 'Gt' cannot be applied to float and float`. This was a reference-side-only bug — the JIT already handled float comparisons correctly via Cranelift's `fcmp` instruction, and mixed int/float comparisons were already promoted to `(Float, Float)` by semantic analysis's `common_numeric_type` before reaching the runtime.

Fix: four one-line additions, each adding a `(Value::Float(a), Value::Float(b))` arm parallel to the existing `(Value::Num(a), Value::Num(b))` arm.

5 new test fixtures: `t_f64_comparison_gt`, `t_f64_comparison_lt`, `t_f64_comparison_gteq`, `t_f64_comparison_mixed_literal` (int vs float after promotion), and `t_f64_equality_regression` (regression guard for the already-working `==`/`!=` path).

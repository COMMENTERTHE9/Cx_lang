## Landed today

**fix(semantic): reject ordering comparisons on Bool/Enum operands** (`3ad89b7`, 15:09 EDT) — CONFIRMED. Closes audit finding 3.3. The semantic layer's ordering-comparison branch (`<`, `>`, `<=`, `>=`) previously fell through to a generic `Ok(SemanticExpr { ty: Bool, ... })` for any operand pair that wasn't numeric, meaning `Bool` and `Enum` operands silently passed semantic analysis and crashed at runtime. The fix restructures the else-branch in `src/frontend/semantic.rs:2281-2298` so that ordering comparisons are accepted only when both operands are numeric; all other type pairs now get a clear rejection at compile time. Four new test fixtures: `t_ordering_reject_bool`, `t_ordering_reject_enum`, `t_ordering_accept_numeric`, `t_equality_accept_bool`. JIT parity: 276/56/0 to 280/56/0 across 336 fixtures.

**docs: record audit findings 3.1/3.2/3.3 as fixed, file new enum-equality gap** (`dd840fc`, 15:57 EDT) — CONFIRMED. Updated `docs/known_issues.md` with complete fix narratives for audit findings 3.1 (scope leaks), 3.2 (width-range enforcement), and 3.3 (ordering rejection). Also filed new known issue #9: enum `==`/`!=` crashes on the interpreter, discovered incidentally during finding 3.3's regression verification.

**ci: call run_matrix.sh directly** (`bdc7c8c`, 16:39 EDT) — CONFIRMED. Closes audit finding 3.4. The CI workflow's verification-matrix step had a 50-line inline reimplementation of `run_matrix.sh` that was already drifting from the canonical script (missing output-verification mode, missing expected-fail handling nuances). Replaced with a single `bash src/tests/run_matrix.sh` call. This eliminates a maintenance risk: future matrix improvements now automatically apply to both local and CI runs.

**fix(runtime): implement enum ==/!=** (`7a4fd5f`, 17:09 EDT) — CONFIRMED. Closes known issue #9, filed just two hours earlier. The interpreter's `ops.rs` had no `(Value::EnumVariant, Value::EnumVariant)` arm in either `Op::EqEq` or `Op::NotEq` — both fell through to the `BadOperands` catch-all and crashed at runtime, even though the semantic layer correctly allowed the comparison. The JIT already handled this correctly via its integer-tag representation. Fix adds explicit arms comparing both `enum_name` and `variant_name` fields. One new fixture: `t_enum_equality.cx`. JIT parity: 280/56/0 to 281/56/0.

**docs: known_issues.md #9 fixed** (`2d2b812`, 17:09 EDT) — CONFIRMED. Updated the issue-#9 entry with the complete fix narrative and verification details.

**JIT array-return fix** (`65736b5` on submain) — **CONFIRMED, branch-local**

The headline fix of the day, committed after the v0.3.3 merge:

A function returning an array `alloca`'d it in its own frame and returned a pointer to it. The frame died on return; the caller read garbage. Both backends exited 0 — the JIT just produced wrong values. Two sequential calls sharing the dead frame produced the second call's values for both. The existing guard covered only phen methods; free functions and impl methods were unguarded and corrupting silently.

No test caught it because the corpus's only array-returning fixture (`t38_generics_array`) returned a length-1 array — exactly the degenerate case where element 0 sits at the top of the dead frame and survives. Length was the variable nobody varied.

The fix generalizes the struct-return convention: `ret_struct_of` ("is this a named struct?") becomes `returns_via_slot` ("does this need a slot?"), because arrays have no `struct_table` entry to be named by. A new `ret_slot_plan` computes size, alignment, and (offset, type) parts once, read by both the caller's `Alloca` and the callee's copy. Six test fixtures were written before the fix and verified failing first: `t_array_return_free_t64`, `t_array_return_free_t8`, `t_array_return_generic_len3`, `t_array_return_impl_method`, `t_array_return_phen_method`, `t_array_return_two_calls`.

Files changed: `src/ir/lower.rs` (+148 lines reworked), six `.cx` fixtures and six `.expected_output` files, `docs/known_issues.md` (§26 added), `README.md`, `docment/ROADMAP.md`.

## Decisions and direction

**v0.3.3 shipped with array returns still broken, by design.** The array-return fix (`65736b5`) landed after the merge. The commit message is unusually detailed about why: the existing test coverage was structurally blind (length-1 arrays can't detect the corruption), and the guard existed on only one of three dispatch paths, making the gap look handled when it was not. The decision to fix it immediately post-tag rather than holding the release is consistent with how the project has handled correctness issues — ship what's verified, fix what's discovered, document the gap.

**No 0.3.4 slot created.** The roadmap update at `39f05cc` explicitly folds the remaining lowering blockers (including array returns and expression receivers) into 0.4. The reasoning is stated in the commit: inventing a version slot would recreate the phantom-slot problem the roadmap reconciliation cleaned up.

**"Remaining lowering blockers" list on submain's roadmap now excludes array returns.** The `65736b5` commit updated the roadmap on submain to remove "array returns from methods" from the 0.4 blocker list, since it's now fixed. Main's copy still lists it because the fix hasn't been merged to main yet.

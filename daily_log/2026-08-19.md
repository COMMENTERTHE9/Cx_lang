## Landed today

**Expression receivers for operator dispatch** (`56983eb`, submain) — CONFIRMED

The operator-gene dispatch machinery required a named variable as the left operand. The method pipeline is name-based end to end, and an expression like `(a + b)` had no representation. This commit adds one: `MethodCall` gains `receiver_expr: Option<Box<SemanticExpr>>`, and each layer handles it with a single branch.

The change touches six source files across four subsystems:

- `semantic.rs` — `try_operator_gene_dispatch` now wraps a non-variable left operand in a `receiver_expr`. Instead of rejecting it, the expression itself becomes the receiver. A synthetic `instance` name (`(+)`, `(-)`, etc.) labels diagnostics; the name is never resolved at runtime when `receiver_expr` is present.
- `semantic_types.rs` — The `MethodCall` variant gains the `receiver_expr` field with a 20-line doc block explaining the named-vs-temporary distinction: present means evaluate in place with no write-back, absent means the existing name-based path unchanged.
- `call.rs` (interpreter) — `call_semantic_method` takes an optional already-evaluated `Value`. The named path is the `None` arm, byte-for-byte identical to the old behaviour. Write-back is skipped for temporaries — not a lost mutation, since a temporary has no name through which one could be observed.
- `lower.rs` — The receiver argument is the expression when present, the synthesized `VarRef` when not. It occupies argument 0 either way, so nothing is reordered and no new control flow is introduced.
- `monomorphize.rs` — The walker descends into the receiver expression, which may itself contain a generic call.
- `eval.rs` — Passes the receiver expression through to the interpreter's method call.

The commit message explains the design choice clearly: the hybrid approach (optional field on the existing form) won over a value-producing expression variant because lowering already treats the receiver as "the expression in argument 0." The alternative would have required statements-in-expression-position — real CFG machinery in lowering, plus new handling in the interpreter and monomorphizer.

## Decisions and direction

The expression-receiver design was an explicit architectural choice, documented in the commit. Two approaches were considered:

1. **Hybrid (chosen):** Add an optional `receiver_expr` field to the existing `MethodCall`. The expression, when present, evaluates in place and occupies argument 0 exactly where the named variable's `VarRef` did. One branch per subsystem, no new control flow, IR and validator untouched.

2. **Value-producing expression variant (rejected):** Would have required statements-in-expression-position — real CFG machinery in lowering, plus new handling in the interpreter and monomorphizer. The commit notes this was "not close."

The temporary/named distinction has a clean semantics: a named receiver writes back its mutations to its variable (the existing behaviour), a temporary does not (because there is nowhere to write to). The mutation canary test pinpoints this reasoning precisely.

With expression receivers done, the remaining lowering blockers for 0.4 are: `.copy`/`.copy.free`/`copy_into` parameter kinds, nested function definitions, `while-in`, function-body `const`, `t128` printing, `char`, and non-identifier string interpolation.

- **Registration pass architecture.** A dedicated whole-graph gene/phen collection pass runs once before any per-file pre-passes. It scans every file in `ResolvedProgram.files` (the complete reachable module graph, already assembled by the existing resolver) and populates a shared registry keyed on `(gene_name, receiver_type)`. The registry lives at `analyze_resolved_program`'s top level, alongside the existing `alias_exports` accumulator — not in per-file `Analyzer` tables, which are deliberately reset per file.

- **Canonical key.** `(gene_name: String, receiver_type: SemanticType)`. No generic-argument component needed since phen receivers are always concrete types. One honest limitation noted: `SemanticType::Struct` carries only a bare name, so two phens for different instantiations of a generic struct would collide — a real gap, but one that belongs to generics v3.

- **Collision semantics.** Duplicate canonical keys anywhere in the reachable module graph are a hard compile error — no silent deduplication, no specialization exceptions (no such system exists). Order-independent by construction since it's a flat scan, not an incremental walk.

- **Deferred items with extension points.** Re-exports (no concept in Cx today), orphan rules (no packages/separate compilation units), specialization/blanket phens (the overlap algorithm is nontrivial — not attempted speculatively). Each deferred item has a named extension point for when its prerequisite infrastructure lands.

- **Semantic-pass ordering.** The complete pass sequence is documented: gene/phen collection (step 0, whole-graph) → enum pre-pass → struct pre-pass → function pre-pass → main analysis pass (per-file, in topo order). The main pass then verifies phen body conformance, resolves `T: GeneName` bounds, and dispatches operator expressions to the correct phen method.

- **Worked examples and test matrix.** Valid multi-gene/same-type and multi-type/same-gene examples, plus invalid exact-duplicate and conflicting-overlap examples (which are the same rejection category with today's feature set). Eight required test fixtures for 0.3.4 implementation documented.

## Decisions and direction

The key decision today is the cross-module coherence architecture itself. Several design choices are worth calling out because they shape how the 0.3.4 implementation will be built:

**Whole-graph registration over per-file registration.** The decision to scan the entire reachable file set in one pass before any per-file analysis begins — rather than accumulating phen registrations incrementally during per-file passes — means coherence checking is inherently order-independent. This is more expensive computationally but eliminates a class of bugs where source-file order or import order could affect whether a collision is detected.

**Flat key equality, not overlap analysis.** Because Cx has no specialization or blanket phens, the collision check is a simple equality test on `(gene, type)` keys. The design explicitly notes that specialization would require a "materially harder" overlap algorithm and punts it to a future system.

**No orphan rule for now.** Rust's orphan rule exists to protect cross-crate coherence. Cx compiles everything as one unit today, so the whole-graph scan already catches all collisions. The orphan rule is deferred until Cx has separately-compiled packages.

This closes the 0.3.3 design phase for gene/phen. The next major move is 0.3.4 implementation — and the design doc now serves as the implementation spec, including pass ordering, key format, diagnostic text, and test fixtures.

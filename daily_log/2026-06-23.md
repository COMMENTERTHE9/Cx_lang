## Decisions and direction

The D2.3b commit makes explicit design decisions that shape the string arc going forward:

**Rep (a), storage (ii)**: a string is a single SSA Ptr to a static `{byte_ptr, byte_len}` descriptor. The "static" part is the key decision — bytes and descriptors are leaked to `&'static` lifetime, which means no deallocation, no stack-lifetime traps, and no GC. This is the JIT-only tradeoff accepted under R6: the baked addresses are process-specific and non-AOT. Dynamic strings and concatenation results will eventually need a different allocation strategy, but for literal strings this is clean and correct.

**Fence-first approach**: rather than attempting partial support for concatenation, comparison, or interpolation, each is explicitly fenced with an `unsupported!` macro pointing to its tracker (D2.3c for concat/compare, D2.3d for interpolation). This keeps the SKIP count honest and prevents silent divergence from interpreter behavior.

**Reuse of Ptr convention**: strings share the same IR type (`Ptr`) as structs and arrays, which means the existing binding, parameter-passing, and return conventions work without special cases. This is consistent with the project's pattern of building on existing infrastructure rather than adding string-specific IR types.

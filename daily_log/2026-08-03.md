## Landed today

**Cycle-only call-depth guarding** (`ab62a6d`, Aug 2 20:32 ET) — CONFIRMED. The uniform depth guard inserted two host callbacks (~11 ns) into every compiled call. A function that cannot reach itself cannot recurse, so it needs no counter. The new implementation builds a static call graph from the IR (after lowering, not from the semantic tree — avoiding the C1-C4 bug family), runs Tarjan's SCC to find all functions in cycles, and only those get the guard.

The implementation is ~130 lines of new code in `host_boundary.rs`:
- `functions_that_can_recurse()` builds the call graph restricted to module-internal edges (host intrinsics like `cx_*` are leaves and cannot close a cycle), then runs an iterative Tarjan's SCC. A function is guarded iff it is in an SCC of size > 1 or carries a self-loop.
- Soundness rests on the call graph being complete. The commit message argues this holds because Cx has no indirect calls: `IrInst::Call.callee` is a `String`, the backend emits no `call_indirect`, and neither `Type` nor `SemanticType` has a function/callable variant.
- The Tarjan is iterative, not recursive — the compiler must not overflow its own stack while adding a guard against stack overflow.

New test fixture `t_mutual_recursion_guard` (mutual recursion is the case a self-loop-only check misses, and a missed cycle means an unguarded crash). New unit test pins: self-loops, length-2 and length-3 mutual recursion, non-recursive callers staying unguarded, and host intrinsics not counting as edges. Boundary agreement re-verified at 255/256 on both recursion shapes across both backends.

Performance measured (minima of 3-5 runs):

| | debug: uniform | debug: cycle-only | release: none | release: uniform | release: cycle-only |
|---|---|---|---|---|---|
| `fib(30)` (recursive) | 141 ms | 139 ms | 98 ms | 104 ms | 112 ms |
| non-recursive, 6M calls | 200 ms | **110 ms** | 103 ms | 128 ms | **106 ms** |

Non-recursive code now matches unguarded. Release compresses the per-call cost to ~3.7 ns (vs ~14.5 ns debug).

## Decisions and direction

One notable design decision from today's work:

**Inline counter deferred, based on evidence.** The original depth-guard docs (§25, from yesterday) filed an inline counter as a follow-up optimization — replacing the two host callbacks with a Cranelift `declare_data` load/add/store. Today's docs commit explicitly defers that work, and the reasoning is grounded in two measurements: (1) cycle-only already eliminates the cost from non-recursive code, which is most code; (2) in release, the residual on recursive code (~3.7 ns/call) is within the benchmark's run-to-run noise. The commit records these numbers as the evidence base for the deferral, not as intuition about it. This is a clear example of the project's pattern of measuring before deciding.

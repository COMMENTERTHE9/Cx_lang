**CONFIRMED — `690f4f3` fix(ir): narrow stored values to destination width (Gate-2a)**

The "negative-store segfault" root cause: `IrInst::Store` carries no width, so Cranelift stores at the value's type. Array-element and struct-field values lower at their computed width (i64 for an integer literal), so an i64 store into a sub-64-bit slot overran by up to 7 bytes — silently corrupting every sub-64-bit array-element and struct-field store. The crash was stack-layout luck: struct-array-field t8/t16 overran into critical stack (0xC0000005 on teardown, correct stdout first), while standalone arrays and struct scalar fields overran benignly and were never caught.

Fix: narrow the value to the destination width before the Store at both construction sites — `lower_array_lit` (Cast elem → elem_ir_ty) and StructInstance (Cast field → field_ir_ty). The `_field_ty` variable sitting unused in the struct loop was the tell. The cast is a no-op when widths already match (t64, Ptr-typed fields). A third-site audit confirmed the `a:[k]=v` and `a:[k]+=v` paths already emit the correct cast from D1.1b's typed lvalue work.

Five new fixtures pin the previously-silent corners (struct-array negative read, standalone t8/t16 negative arrays, struct scalar t8/t16 negative fields). `t_array_elem_field_in_range` converts from SKIP to PASS. Parity 182/98/0 → 188/97/0 across 285 fixtures.

**CONFIRMED — `51e4e24` fix(ir): bounds-check array indexing, trap on out-of-range (Gate-2b)**

The last gate commit. The three remaining `.jit_known_unsound` markers were genuine out-of-bounds accesses (`a:[5]` on a 3-element array). The interpreter raises `IndexOutOfBounds` cleanly; the JIT had no bounds check — reads returned garbage, writes corrupted memory and crashed.

New `emit_bounds_check` helper called at both runtime-index sites (`resolve_array_element_ptr` for writes/compound-assign, `lower_index` for reads) before the PtrAdd that computes the element address. Out-of-bounds routes to the Trap terminator via `cx_trap` (exit 126). Two nested checks handle signedness: `idx < 0` then `idx >= count` — a negative index traps rather than wrapping to a huge unsigned offset.

All three `jit_known_unsound` markers removed. One new fixture `t_oob_negative_index` pins the negative-index trap. Parity 188/97/0 → 192/94/0 across 286 fixtures. Performance cost: ~5% on access-dominated loops (two compares + two predictably-not-taken branches per array access), measured via within-session A/B on a 40M-read loop.

## Decisions and direction

**Store-width narrowing as codegen-correctness, not a trap:** Gate-2a is explicitly a valid-program fix — the miscompilation produced the right stdout but corrupted adjacent stack. This is distinguished from Gate-2b, which traps on genuinely bad operations. The distinction matters for how the parity harness classifies results.

**Signed bounds checking with two comparisons:** The IR has no unsigned compare op, so the standard single-compare trick (`(unsigned)idx >= count`) is unavailable. The commit message explicitly notes this as a possible future optimization — the current two-compare approach is correct and the 5% overhead is acceptable for memory safety.

**Gate completion as merge-readiness signal:** With zero unsound markers remaining, submain's JIT is now free of all known crash classes. This is the strongest merge-readiness signal since the v0.1.0 release. The 14-commit gap is growing and represents a significant amount of tested, stable work.

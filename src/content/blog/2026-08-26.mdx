The CI pipeline had a silent bug in the stale-base check, and it got fixed and merged today. No language or compiler work landed, but the fix is worth understanding because it was broken in a way that looked correct.

## Stale-base check was measuring the wrong thing

The `stale-base` job in `ci.yml` was supposed to flag PRs whose branch had drifted too far behind their target. Instead, it was measuring how far `submain` led `main` on every single PR, regardless of which branch the PR actually targeted. That meant it silently passed on all 93 open PRs targeting main, reporting a repo-level property rather than anything about the PR itself.

The root cause was two-fold. First, the job always fetched `origin/submain` and computed `HEAD..origin/submain`, ignoring `github.base_ref` entirely. Second, `actions/checkout` on a `pull_request` trigger checks out the merge commit, which already contains the base, so the count would read zero for every mergeable PR and pass vacuously.

The fix reads the actual base branch from `github.base_ref` and checks out the PR head commit directly (`github.event.pull_request.head.sha`) so the base's commits are genuinely absent from HEAD. Without both changes together the count stays meaningless. The threshold stays at 20 commits. Merged via PR #388 as commit `f691ef0`, touching `.github/workflows/ci.yml` (+13/-7).
